## Problem Statement

An experienced put seller on HK and US stocks wants a repeatable, justified way to pick which puts to sell,
instead of ad-hoc judgement. The full design (docs/00 to 07) covers scanner, backtester and UI. This session
reviewed that design and cut it to a first milestone that can be used for real within days.

## What Makes This Cool

A terminal command that, every morning, prints a ranked list of puts to sell on your own names, each with a
reasons table you can argue with, priced from real chains where they exist and from your own past fills where
they do not. Your trade history stops being a spreadsheet and becomes the calibration set.

## Constraints

- Node.js + TypeScript + PostgreSQL 16 on a Windows Server host; no Docker assumption.
- Free data (Yahoo) only in milestone 1. US chains are real; HK chains are pasted CSV or synthetic.
- HK reports semi-annually; HK earnings dates are often missing from free data.
- The app never places orders. Sizing uses notional, never broker margin.

## Premises (agreed)

1. Decision tool for one person; no order execution.
2. Risk and sizing on full notional (strike x multiplier); margin return is display only.
3. First milestone is a CLI scanner with justifications; backtest engine after live use.
4. Past trades are imported first and are ground truth for HK price calibration and rule attribution.

## Approaches Considered

- **A. Scanner first, journal seeded (chosen).** Phases 0 to 2 of the roadmap (journal and CSV chain import are inside Phase 1). 9 to 12 working days, risk low.
- **B. Full design in order.** Rejected: months before first use, HK backtests synthetic anyway.
- **C. Journal first, rules derived from history.** Rejected as the primary path: sample small and biased; its import step is folded into A.

## Recommended Approach

Milestone 1 is a CLI and a database. No HTTP server, no job queue (those arrive in Phase 3 with alerts);
`pnpm cli ingest --all` runs from Windows Task Scheduler. Build `docs/06-roadmap.md` Phases 0 to 2 as revised:
1. Skeleton: single package `src/{core,indicators,providers,skills,db,cli}`, Drizzle schema in `src/db/schema.ts`
   as the schema source of truth with generated migrations (`docs/03-schema.sql` is reference), CLI entry point,
   native Postgres; migration seeds the `default` strategy params and the single `portfolio_settings` row
   (equity set via `cli settings`).
2. Data in: Yahoo bars for stocks and for SPY, ^VIX, 2800.HK, ^HSI (VHSI symbol verified here, HKEX CSV seed as
   fallback), fundamentals, US chains, FX with 10-year backfill; HK board-lot seed; static calendars;
   **journal CSV import** (generic template, positions and journal-tier quotes only); **HK chain CSV import**
   with authoritative `--spot`/`--date` flags; manual events entry; a fundamentals coverage report for 10 names.
3. Indicators, Black-Scholes and in-app greeks (Yahoo and CSV supply none); skills S0 to S7
   (`docs/04-skills-spec.md`) with period-aware fundamentals, data gaps degrading to WARN rather than FAIL,
   sector-switched solvency, open-position exclusion, notional-based economics; `pnpm cli scan` (database only,
   never fetches) and `pnpm cli explain`; `pnpm cli journal calibrate` writes `pricing_calibration` for fills and
   pasted chains; journal attribution report.

Signal event studies and the portfolio backtester are Phase 4. Use the scanner daily for 3 to 4 weeks first.

## Success Criteria

- `pnpm cli scan` on a real watchlist of 20+ names, reading stored data only, prints a ranked shortlist with a reasons table and data tier per row in under a minute.
- Journal import reproduces your own realised P&L totals under the rules in `01 §G2`.
- At least one HK name priced from a pasted chain CSV, and `pnpm cli journal calibrate` has written its synthetic price beside it in `pricing_calibration`.
- Every FAIL names its binding rule.

### Failure modes (per new codepath)
| Codepath | Realistic failure | Test | Handling | User sees |
|---|---|---|---|---|
| Yahoo ingest | crumb/429 outage overnight | provider contract test with failure fixture | stooq fallback, job_runs row | scan header lists stale names, drops them |
| Freshness gate | holiday mis-marked in calendar | calendar tests 2010–2027 | gate uses last trading day per market | false `data.stale` with the date printed, fixable |
| CSV chain import | crossed quotes, wrong units | one test per rule | reject with line numbers | clear report, nothing stored |
| Journal import | assignment booked wrong | P&L fixture incl. assigned rows | mtm_at_assignment formula | totals printed per market to compare with broker |
| reported_at estimate | filing visible later than reality | lag + first_seen clamp tests | min(estimate, first_seen) | flagged `reported_at_estimated` in reasons |
| Cache invalidation | writer forgets to call it | test enumerates writers | single `invalidateSkillRuns` helper | stale memo, caught by test |
| Runner full mode | FAILed name missing scores in explain | mode test | full mode runs all | explain always complete |
| S3 rvOnly | fake volatility edge | tier test | NA + renormalised weights | `iv.unscored` reason |
| S5/S6 caching | stale recommendation after a fill | never-cache test | recompute each run | shortlist reflects positions |
| Lookahead | any skill reads beyond asOf | future-perturbation property test | DataAccess bound | test failure, never silent |
Critical gaps (no test, no handling, silent): none remaining.

### Worktree parallelization strategy
| Step | Modules touched | Depends on |
|---|---|---|
| Skeleton, Drizzle schema, migrations, seeds | src/db, root config | — |
| Calendars and contract specs | src/core | — |
| Indicators + goldens + BS/IV/YZ | src/indicators, tests/fixtures | — |
| Providers: yahoo, stooq, csv, journal, invalidation | src/providers, src/db | schema |
| Skills S0–S7 + runner + freshness gate | src/skills | core, indicators, providers |
| CLI commands | src/cli | skills, providers |
Lane A: core → indicators (independent). Lane B: db schema → providers (sequential, shared src/db). Lane C: skills (after A and B). Lane D: cli (after C). Launch A and B in parallel worktrees, merge, then C, then D. No module overlap between A and B.

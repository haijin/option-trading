- Journal CSV (docs/01 G2) details the spec left open, decided by the importer build: optional columns `spot`, `underlying_close`, `closed_contracts`, `notes`. Assigned rows book P&L = (credit - max(0, strike - U)) x multiplier x contracts - fees where U is `underlying_close` or the stored bar close (else the row is rejected `journal.assignedNoUnderlying`). Fees are TOTAL per row in whole cents. A partial close is expressed with `closed_contracts` and split into a closed and an open leg (fees allocated by exact proportion, remainder to the closed leg). `rolled_to_row` is a 1-based DATA-row number (comments, blanks and header not counted), resolved before same-day fills merge and before splits; a roll target that is itself split resolves to its closed leg. Same-day fills merge by (market, symbol, expiry, strike, open_date, close_date, outcome) with contract-weighted prices. All P&L arithmetic is BigInt micro-units, rounded half away from zero to the cent per leg; totals are sums of rounded legs. Any error rejects the whole file with physical line numbers; nothing is stored.

## 2026-10-11 — login page: password, Google, email link (autonomous)
- Request: "Create Login page, it allow user name + password, Google and Email link". Built as a real gate, not a screen: every data route answers 401 `unauthenticated` without a session cookie; `/api/health` (minimal without a session) and `/api/auth/*` are public; static files stay public (they hold no data). The gate is a hook attached to the data routes themselves (all registered inside one Fastify plugin, `app.ts`), never a test of the URL string: see "Independent security review" below. `OT_AUTH=off` removes the gate, and the offline e2e tests run with it off (`ServerDeps.auth === null`) so they keep exercising the data endpoints directly.
- `.env` already held `APP_URL=https://o.tokoo.app`, read by no code. Interpreted as the public address of the app (a tunnel or proxy to 127.0.0.1:3004), the likely reason a login was asked for. It is used for three things only: the emailed link origin, the Google redirect URI, and one extra allowed `Host` (exact match, only while the login is on). With `OT_AUTH=off` the public host is refused. If that reading is wrong the effect is nil: the host is reachable only if the user routes it here.
- One owner, no sign-up. The first account is created from the login page only, and needs two proofs: the request looks local (loopback `Host`, loopback socket address, none of the proxy headers `X-Forwarded-*`, `Forwarded`, `Via`, `X-Real-IP`, `CF-*`) AND it carries the setup code the server prints in its terminal at start-up (about 40 bits, 5 wrong tries per 15 minutes). Neither is enough alone: "looks local" is inferred from headers, and a proxy that rewrites `Host` and adds nothing (stock nginx `proxy_pass`) looks local. Google and email links never create an account (an earlier draft let them, from the machine itself; dropped with the setup code). After one account exists nothing creates another; Google and email links sign in to it by verified email (Google also by `sub`). Reason: the app can start paid AI runs and write the portfolio; with a public URL, "first visitor becomes owner" would be a takeover. Creation runs under a Postgres advisory lock, so two simultaneous first visits cannot both win (tested).
- Passwords: scrypt (N=2^16, r=8, p=1) from node:crypto, self-describing hash string, length-only policy (8 to 128, NIST 800-63B). No new dependency for hashing. An unknown user or a password-less account still costs one full hash check, and answers with the same message as a wrong password.
- Sessions: 256-bit random cookie `ot_session` (HttpOnly, SameSite=Lax, `Secure` when the request came in through an https `APP_URL`), 30 days, only its SHA-256 stored. Sign-out deletes the row. Existing CSRF defences (same-origin `Origin`, JSON-only writes) cover the login endpoints too.
- Email link: token in the URL fragment (`/#/login?token=...`), which is never sent to a server or logged by a proxy, and is spent by a POST from the page, so a mail scanner that only fetches the URL cannot burn it. Single use, 15 minutes, stored hashed. The request endpoint answers identically whether or not the address has an account, sends in the background (no timing difference), and is limited to 5 per address per 15 minutes. Delivery is SMTP through nodemailer when `OT_SMTP_URL` is set; otherwise the link is printed in the server terminal and the login page says so (the only difference the API reveals is a config fact, `delivery: "console"`).
- Google: authorization code + PKCE (S256) + `state` + `nonce`, no OAuth library, round trip is two browser navigations (no token ever passes through page script). The ID token comes straight from Google's token endpoint over TLS with the client secret, which Google accepts in place of a signature check; issuer, audience, expiry, nonce and `email_verified` are still checked. The button is shown disabled with the reason until `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` exist.
- Brute force (in memory, per 15 minutes): 10 failures per (caller, name), 50 per name overall, 30 per caller overall; email-link requests 5 per (caller, address), 10 per address, 20 per caller; 5 wrong setup codes. The caller is the last `X-Forwarded-For` entry (the one our own proxy appended) or the socket address. An earlier draft keyed by name alone, which let a stranger lock the owner out of both password and email-link sign-in; per-caller keys fix that, the per-name ceiling still bounds a guesser who rotates fake addresses. When the table is full the oldest key is dropped (not all of them).
- Unauthenticated requests to an unknown `/api/...` path get 404, not 401 (no route matched, so there is no gate and nothing to leak).
- The server will not start if the sign-in tables are missing; it says to run `pnpm db:migrate` (or set `OT_AUTH=off`). Not auto-migrating keeps schema changes an explicit step, as in milestone 1.
- Verification ran on a scratch database `ot_live_auth` (real server, real UI in the browser pane, dropped afterwards); the user's real database (`option_trading`, :5433) was not touched while testing. Afterwards `pnpm db:migrate` was run once on the real database (migration 0005, three new tables): migrations 5 to 6, and the row counts of instruments, watchlist, positions, price_bars, portfolio_settings, research_runs, fair_values and strategy_params were identical before and after.

## 2026-10-12 — Phase 3 (marks, alerts, wheel, jobs) and Phase 4 (backtests) (autonomous)
- Request: "move on the phase 3 and phase 4". Built both from docs/06 with the existing pipeline, tables and API; no new architecture beyond a `jobs` layer.
- **Marks** use a stored chain quote for the exact contract when it is at most 5 calendar days old (mid when both sides quote, else last; journal fills never mark), otherwise the model: Barone-Adesi-Whaley American put at the skew-adjusted sigma, sigma = stored IV30 if within 7 days, else 30-day realised vol x the market's IV/RV ratio. A mark is a mid with no haircut (it values the position, it is not a fill). A put past its expiry is skipped with "record how it ended", never priced. Stale marks (over 7 days) stay on screen with their date but do not drive the mark-based alerts.
- **Alerts** are one pure function (`src/core/alerts.ts`) used by the app view and the daily job, so the two cannot disagree. Stop = loss reaches 2x the credit (mark >= 3x the credit received). Assignment risk = in the money with extrinsic value under 1% of the strike (the docs/05 early-exercise heuristic without its "10% ITM" leg, because a live alert should fire sooner than a backtest assumption). "New earnings date" = an earnings date inside the put's life whose `known_at` is after the fill date. Push sends only alerts absent from the previous mark.
- **The wheel**: assignment creates a `stock_lots` row (migration 0006). The lot's basis is the underlying close at assignment, NOT strike less premium: the journal already books the put's P&L as (premium - intrinsic at assignment), so basing the shares on the strike would count the assignment loss twice. Strike less net premium is derived from the put for display as "effective cost". Journal-imported assigned rows do not create lots (history, shares presumably sold). Covered calls are not modelled (docs/06 asks only for conversion on assignment).
- **Scheduler**: pg-boss 12, opt-in `OT_JOBS=on` so the `pgboss` schema is never created unasked. Schedule per docs/02 section 4, each market in its own time zone (cron + `tz`). Job bodies are plain functions over a `CliContext`, shared by pg-boss, `pnpm cli jobs run` and "Mark now"; each records a `job_runs` row and returns a failed outcome instead of throwing, so a failing job never poisons the queue. The `/health` endpoint already existed (milestone 2).
- **Push channels**: Telegram (bot API) and SMTP email, both off unless configured. The Telegram token sits in the request URL, so errors report the HTTP status only (tested). Neither channel was exercised live: no credentials here.
- **Architecture guard**: tests/structure.test.ts now lets `jobs` import providers (an application layer like cli and server, docs/02 section 1). The test caught two real violations of my own first draft (backtest and cli importing server types, the notifier importing the server's mailer); they were fixed by moving the backtest view types into `src/backtest/views.ts` (re-exported by api-types.ts) and giving the notifier its own nodemailer call, not by loosening the rule further.
- **Backtest engine** (`src/backtest/`): pure daily loop with an injected `EntrySource`, so the live pipeline replay, the naive benchmark and the sensitivity re-runs share one engine. Order per day: settle expiries, fill exits triggered on an earlier close (next-close fills, no same-bar fills), mark and test the rules (stop, take profit, time exit), then entries. Entries fill at the close, cash-secured at full notional. Cash earns a flat rate (the HK or US risk-free parameter by base currency) every calendar day. Assignment settles at intrinsic and the loss is booked at once (same convention as the journal); no share position is simulated.
- **Observe mode** records rejected entries as shadow trades that never touch cash (they are stored with `scores.shadow = true`, hidden from the trades list by default). **Sensitivity** re-prices the base run's memoised entries at sigma x0.8 and x1.2, so it isolates pricing error and holds sizes fixed (stated in the caveats). **Walk-forward** grid defaults to four combinations (deltaMax 0.25/0.30 x maxPerNamePct 0.03/0.05), capped at 24 by the module; only out-of-sample numbers are reported, with the overfitting flag when out-of-sample Sharpe is under half of in-sample.
